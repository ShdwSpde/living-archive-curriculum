## Reading

### Running the SQL Migration

The `document_chunks` table doesn't exist in your Supabase project until you run the migration. The migration SQL file lives at `supabase/migrations/create_document_chunks.sql` in the project repository. To run it:

1. Log in to app.supabase.com and open your project
2. Click "SQL Editor" in the left sidebar
3. Paste the contents of the migration file into the editor
4. Click "Run"
5. You should see "Success. No rows returned."

**What the migration creates:**
- The `document_chunks` table with all necessary columns
- The `pgvector` extension (if not already enabled)
- A vector index for fast similarity search
- The `match_documents` and `get_corpus_titles` RPC functions
- A unique constraint on `content_hash` for dedup

If you see an error saying `extension "vector" does not exist`, the pgvector extension isn't enabled in your project. Go to Database → Extensions → search "vector" → enable it, then re-run the migration.

### Understanding Each Column

After running ingestion (Unit 5), open the `document_chunks` table in Table Editor and examine some rows. Here is what each column means in practice:

**`id`** — A UUID auto-generated by Supabase on each insert. You don't set this; the database assigns it. It uniquely identifies each chunk row.

**`source_title`** — The display title of the work this chunk came from. Set by the ingestion script's TITLE_MAP (or derived from the filename). This is what users see in citations: "Source: The Souls of Black Folk."

**`chapter`** — The chapter or section within the work, detected by the chunk script's regex logic. May be `null` for periodicals or short texts without chapter structure. Shown in the corpus sidebar and in detailed citation views.

**`content`** — The actual text of the chunk: approximately 800 tokens of prose from the source text. This is what the language model reads when generating responses. Quality here determines answer quality.

**`content_hash`** — An MD5 hash of the `content` field. Used for dedup: the unique constraint prevents two rows with the same content hash. If you see a duplicate content error during ingestion, this constraint caught it.

**`embedding`** — A vector of 768 floating-point numbers representing the semantic meaning of the chunk content. This is what pgvector uses for similarity search. You will never read this column directly; it's used only for computation.

**`metadata`** — A JSONB column for additional fields (source URL, publication year, volume number). Not all ingestion scripts populate this field, but it's available for extension.

**`created_at`** — The timestamp of the insert. Useful for debugging: if you see all rows with the same timestamp, they were probably inserted in a single bulk operation rather than individually.

### Adjusting the Similarity Threshold

The similarity threshold determines how close a passage must be to a query to be returned. The default is 0.7. To adjust it:

1. Open the Supabase SQL Editor
2. Run a test query manually with a different threshold:

```sql
SELECT
  source_title,
  chapter,
  content,
  1 - (embedding <=> '[...query vector here...]') AS similarity
FROM document_chunks
WHERE 1 - (embedding <=> '[...query vector here...]') > 0.6
ORDER BY similarity DESC
LIMIT 5;
```

(Note: you can't easily paste a real query vector into the SQL editor manually — this test is better done through the application's test query function. See the Developer pathway for the RPC approach.)

**A practical way to tune the threshold without the SQL editor:** Use the live archive and note when it says "no relevant passages found" for a question you think should be answerable. If this happens frequently, the threshold may be too high. If responses include obviously irrelevant passages, it's too low. Communicate your observations to the developer, who can adjust the threshold parameter in the API call.

**Starting recommendation:**
- 0.7: good default; works for most questions on a clean corpus
- 0.5–0.6: if you need broader coverage on a sparse corpus; increases false positives
- 0.75–0.8: if you're seeing irrelevant passages in responses; reduces recall

Keep track of your threshold changes and what effect they had — this is valuable calibration data.

### What to Do When You See Unexpected Results

If a test query returns results that seem wrong — irrelevant passages, wrong source titles, too few results — the diagnostic sequence is:

1. **Check row count:** Is the corpus fully ingested? `SELECT COUNT(*) FROM document_chunks;`
2. **Check for the source:** If you expect a result from a specific work: `SELECT COUNT(*) FROM document_chunks WHERE source_title ILIKE '%souls%';` — if 0, the work wasn't ingested.
3. **Lower the threshold:** Try 0.5 — do results appear? If so, the embedding is working but the threshold is too strict.
4. **Check content quality:** Find the work's rows and read the `content` field. Is it readable?
5. **Check source_title mapping:** Does the `source_title` field match what you expect? A garbled title means the TITLE_MAP needs updating.

Each of these checks can be done in the Supabase SQL editor without any code changes.
